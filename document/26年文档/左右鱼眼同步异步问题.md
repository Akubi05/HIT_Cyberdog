## 3. 根因

根因不是 raw 保存逻辑，也不是 SCP 没拷贝到文件；本机确实几乎没有收到 5558 的右鱼眼帧。

根因是：

```text
camera_api camera_id=2 + OpenCamera(sync=1)
```

在 `192.168.96.13` 这台狗上会触发 NvCapture/SCF timeout，导致 right_fisheye bridge 只能偶发发送 1 到 5 帧，然后长期卡住。

手工复测结果：

| 测试项 | 结果 |
|---|---|
| `camera_id=2 sync=1` | 复现 timeout，只发极少帧 |
| `camera_id=2 sync=0` | 正常，约 30fps 采集、约 8fps 发送 |
| `camera_id=3 sync=1` | 正常，约 30fps 采集、约 8fps 发送 |
| 并发 `left id3 sync1 + right id2 sync0` | 两路同时正常 |

补充说明：用 `nvarguscamerasrc sensor-id=2/3` 直接测试时两路都能保存有效 JPEG。这只能说明底层 CSI/Argus 不是彻底坏掉，不能证明项目的 `camera_api_zmq_bridge --camera-id 2 --sync 1` 正常。`nvarguscamerasrc sensor-id` 和项目里的 `camera_api camera_id` 不要直接混用判断。

### 3.1 sync 是什么

这里的 `sync` 不是 ZMQ 发送同步，也不是本机 receiver 的线程同步，更不是业务层“左右图像严格同一时间戳”的同步。

它是小米 `camera_api` 的底层打开参数：

```cpp
CameraHandle OpenCamera(int camera_id, int & status, bool sync = false);
```

项目的 C++ bridge 中对应调用是：

```cpp
auto handle = cyberdog::camera::OpenCamera(options.camera_id, status, options.sync);
StartStream(handle, format, width, height, frame_callback, &state);
```

因此：

| 参数 | 含义 |
|---|---|
| `--sync 1` | 让 `camera_api` 按 sync 模式打开该路 camera，再 `StartStream` 出帧。该模式会影响底层 camera_api/Argus 的 sensor mode 选择和 capture 调度。 |
| `--sync 0` | 让 `camera_api` 按 async/非 sync 模式打开该路 camera。仍然是同一颗 CSI camera、同一个 camera_id、同样通过 callback 出 `cv::Mat`，只是底层采集模式不同。 |

从既有 camera_api 调查记录看，`camera_id=2/3` 在 sync 模式下的 sensor mode 选择逻辑和非 sync 模式不同；本次 `192.168.96.13` 上 `camera_id=2 sync=1` 进入了会 timeout 的采集路径，而 `camera_id=2 sync=0` 会选择稳定路径。

### 3.2 左右鱼眼数据链路

当前 direct 模式的左右鱼眼链路是两条独立进程链路：

```text
left_fisheye:
CSI fisheye camera
  -> Xiaomi camera_api OpenCamera(camera_id=3, sync=1)
  -> StartStream(width=640,height=400,encoding=bgr8)
  -> frame_callback(cv::Mat)
  -> /SDCARD/build/camera_api_zmq_bridge
  -> ZMQ PUB tcp://0.0.0.0:5557
  -> PC Stage4ZmqFrameReceiver
  -> raw/left_fisheye/*.jpg
  -> Stage3/4/5 业务视觉

right_fisheye:
CSI fisheye camera
  -> Xiaomi camera_api OpenCamera(camera_id=2, sync=0)
  -> StartStream(width=640,height=400,encoding=bgr8)
  -> frame_callback(cv::Mat)
  -> /SDCARD/build/camera_api_zmq_bridge
  -> ZMQ PUB tcp://0.0.0.0:5558
  -> PC Stage4ZmqFrameReceiver
  -> raw/right_fisheye/*.jpg
  -> Stage1/3/4/5 业务视觉
```

这两条链路是独立的 bridge 进程，分别占用不同 camera_id 和不同 ZMQ port。把右鱼眼改成 `sync=0` 不会把左右图像合成一条链路，也不会改变右鱼眼的 camera_id、分辨率、encoding、ZMQ port 或 raw 协议。

# 解释 camera_api 内部采集模式 sync/async ,摄像头内部到底是怎么同步异步工作的

这里的同步/异步，准确说是：

  camera_api 的采集请求调度 和 底层 CSI/VI/Argus 硬件帧事件 之间的同步/异步。

  不是左图和右图同步，也不是网络同步。

  摄像头内部链路
  一帧图像大概这样走：

  camera sensor 曝光/读出
    -> MIPI CSI
    -> NVIDIA VI/NvCSI capture
    -> Argus / camera_api
    -> NvBuffer / ISP / format transform
    -> cv::Mat callback
    -> camera_api_zmq_bridge
    -> ZMQ
    -> PC receiver

  sync=1 时，camera_api 会走更严格的同步采集路径：发出 capture request 后，等待
  底层硬件报告对应帧的 frame start / frame end / capture status。你日志里的报错
  正是这里：

  Timeout waiting on frame start
  Timeout waiting on frame end
  capture waiting for status timeout
  syncpoint wait timeout

  也就是说，它同步的是：

  camera_api 发出的 capture sequence
  和
  NvCSI/VI 硬件实际产生的 frame start/frame end 事件

  sync=0 时，camera_api 走非 sync 采集路径。它仍然会等帧、仍然通过 callback 给图
  像，只是不启用这条严格的同步 capture 调度路径。

  这次为什么 sync=0 能修：

  - camera_id=2 sync=1 日志显示选了 sensor mode 0，即 1280x800 same aspect ratio
  - 然后底层等不到对应的 frame start/end，进入 timeout
  - camera_id=2 sync=0 日志显示选了 sensor mode 1，即 640x400 same resolution
  - 这条路径能稳定 30fps callback

  所以这里的核心不是“同步好、异步差”，而是 这台狗的右鱼眼 camera_id=2 在
  camera_api sync 模式下走到了不稳定的底层采集路径。改成 sync=0 后，仍然是右鱼
  眼、仍然是 camera_id=2、仍然是 640x400，只是避开了会卡死的同步等待路径。

  左鱼眼没改，是因为 camera_id=3 sync=1 实测稳定。

# 详细解释为什么都是等帧,同步调度 收不到图片 ,异步调度可以收到

关键点：同步/异步都要等帧，但“等的东西”不一样。

  sync=1 等的是：
  我发出的某个 capture request，必须收到对应 sequence 的硬件 frame start / frame
  end / status。

  sync=0 等的是：
  底层 stream 里有 frame buffer 到 callback 就处理，不强绑定这次 request 必须按
  同步序列完成。

  所以会出现：

  sync=1: 硬件事件等不到 -> 整条 capture 卡住
  sync=0: buffer 持续到 callback -> 能收到图片

  更具体一点。

  sync=1 路径大概像这样：

  camera_api 发 capture request #1
    -> VI/NvCSI 等 sensor frame start #1
    -> 等 sensor frame end #1
    -> 等 capture status #1
    -> 成功后 buffer 交给 callback

  这次右鱼眼坏在中间：

  Timeout waiting on frame start
  Timeout waiting on frame end
  capture waiting for status timeout

  意思是 camera_api/Argus 认为“我已经发了第 N 个采集请求”，但 VI/NvCSI 没等到它
  期望的那个硬件帧事件。同步路径通常很严格：某个 sequence 等不到，就会阻塞、
  abort、状态机变坏，后面帧也很难继续正常出来。

  sync=0 路径更像：

  打开 camera stream
    -> 底层持续产出 buffer
    -> 哪个 buffer 到了就回调 callback
    -> bridge 发 ZMQ

  它不把上层调用卡死在“第 N 个 request 必须等到第 N 个 frame end”这个同步点上，
  所以能绕过这台机器上 camera_id=2 sync=1 的等待死点。

  这次还有一个很重要的证据：两个模式选的 sensor mode 不一样。

  camera_id=2 sync=1 日志里是：

  Found best sensor mode 0 with same aspect ratio (1280/800)

  也就是请求 640x400，但 sync 模式走了 1280x800 这条采集路径，再做输出处理。

  camera_id=2 sync=0 日志里是：

  Found best sensor mode 1 with same resolution (640/400)

  也就是直接走 640x400 原生/匹配路径。

  所以这次更准确的解释是：

  sync=1 不只是“等待方式更严格”，它还让 camera_api 对 camera_id=2 选择了另一条底
  层 sensor mode / capture 路径。这条路径在这台狗的右鱼眼上等不到正确的 VI/NvCSI
  帧事件，于是 timeout。sync=0 选到 640x400 same resolution 路径，硬件能正常产出
  buffer，所以图片能回来。

  可以这么理解：

  摄像头本体没死
  MIPI/CSI 基本链路也没死
  camera_id=2 也没错

  坏的是：
  camera_id=2 + sync=1 + mode0/同步 capture 等待路径

  改成：

  camera_id=2 + sync=0 + mode1/非同步 stream callback 路径

  所以能收到图。

  这也是为什么不能说“右鱼眼硬件坏了”。如果硬件真的不出帧，sync=0 也不会稳定
  30fps。现在现象说明是 camera_api 某个同步采集路径和这路右鱼眼不兼容。

# 为什么异步也在等待,却能收到图片,是因为不管是异步和同步,中间都缺帧了,但是异步缺帧不影响后续?

是的，你这个理解基本对，但要稍微修正一下：

  不一定是物理上真的“缺帧”了；更准确是 sync 模式认为它等的那一帧/那个事件缺了或
  不匹配了，而 async 模式不把后续流程卡死在这个序号事件上。

  可以这样理解。

  sync=1 是“按号取餐”：

  我要 capture sequence #1
  必须等到 #1 的 frame start
  必须等到 #1 的 frame end
  必须等到 #1 的 status
  然后才交付这一帧

  如果中间某个事件没来、晚了、编号不符合预期、mode 不匹配、VI/CSI 状态不同步，就
  会：

  #1 等不到
  -> timeout
  -> capture scheduler 状态异常
  -> 后面的 #2/#3/#4 也被影响
  -> callback 基本停掉

  sync=0 更像“流式收帧”：

  stream 已经打开
  底层哪个 buffer 完成了
  就把这个 buffer 交给 callback

  如果某一帧丢了、某个事件没对上、某个 buffer 没回来，通常表现为：

  这帧没了/跳过
  下一帧来了继续 callback

  所以你的说法可以改成：

  > async 也在等帧，但它不是严格等待“这一条 capture request 对应的这一帧必须完
  > 成”；它更像等可用 buffer。某次事件丢失或不匹配时，sync 会卡在那个等待点，
  > async 可以跳过异常帧继续处理后续 buffer。

  这次日志也支持这个判断。sync=1 报的是：

  Timeout waiting on frame start sensor guid 1, capture sequence ID = 1
  Timeout waiting on frame end sensor guid 1, capture sequence ID = 1
  ...
  capture sequence ID = 4 / 6 / 8

  说明它在等具体 sequence 的硬件事件，而且这些 sequence 连续失败。然后还出现：

  Free request list is empty
  CaptureScheduler frameStart failed

  这表示同步 capture 调度队列已经被卡坏了。

  而 sync=0 这条链路没有这些 sequence timeout，callback 能持续到：

  captured=50 sent=13 capture_fps=31.xx

  所以结论是：

  是的，异步模式即使中间有单帧丢失或某个硬件事件没对齐，也更可能继续消费后续帧；
  同步模式会把“某个 sequence 必须完整完成”作为强条件，一旦等不到就卡住整个采集调
  度。

  另外还有一个现实因素：这台狗上 sync=1 和 sync=0 选的 sensor mode 不一样：

  sync=1 -> mode 0, 1280x800
  sync=0 -> mode 1, 640x400

  所以不仅是“容忍缺帧”的差别，也可能是 sync=1 选到的那条 mode/capture 路径本身更
  容易产生 sequence 不匹配或 frame event timeout。

# 那 另外还有一个现实因素：这台狗上 sync=1 和 sync=0 选的 sensor mode 不一样： sync=1 -> mode 0, 1280x800 sync=0 -> mode 1, 640x400 这个不一样会有什么影响吗

会有影响，而且这次很可能就是关键影响之一。

  虽然最后保存出来都是 640x400，但底层采集路径不一样：

  sync=1 -> sensor mode 0: 1280x800
            传感器先按 1280x800 出图
            camera_api/Argus 再处理成 640x400

  sync=0 -> sensor mode 1: 640x400
            传感器直接按 640x400 出图
            后面基本按目标尺寸走

  影响主要有几类。

  1. 硬件时序不同
  1280x800 和 640x400 的传感器读出窗口、binning/skipping、line time、frame
  timing 都可能不同。即使标称都是 30fps，底层 CSI/VI 等待的 frame start/frame
  end 时序也不一样。

  这次 sync=1/mode0 卡在：

  Timeout waiting on frame start
  Timeout waiting on frame end

  说明 VI/NvCSI 等的硬件帧事件没有按它预期到来。

  2. 数据量不同
  1280x800 是 640x400 的 4 倍像素量。底层需要更大的 buffer、更高 CSI/VI 带宽、更
  多转换工作。后面再转成 640x400，链路更复杂。

  3. 图像几何可能不同
  即使输出都是 640x400：

  - mode0 1280x800 -> 640x400 可能是缩放
  - mode1 640x400 -> 640x400 可能是原生窗口/裁剪/binning

  两者的视场、畸变、边缘内容、细节尺度可能略有不同。对黄线检测这类算法，通常不一
  定致命，但需要实图对比确认。

  4. 曝光/增益/ISP 行为可能不同
  不同 sensor mode 可能有不同曝光范围、行周期、增益策略、ISP 参数。画面亮度、噪
  声、运动模糊可能变化。

  5. 同步路径状态机更严格
  sync=1 + mode0 不只是分辨率不同，还走同步 capture sequence。它要求某个 request
  对应的硬件事件按序完成。mode0 如果事件/时序和当前配置不匹配，就会卡住；sync=0
  + mode1 走流式回调，稳定产出 buffer。

  所以总结：

  最后 JPEG 都是 640x400，不代表底层采集一样。sync=1 是先采 1280x800 再变成
  640x400；sync=0 是直接采 640x400。前者链路更重、时序不同、同步等待更严格，因此
  更容易在这台狗的右鱼眼上 timeout。

  对当前任务来说，最实际的判断是：sync=0/mode1 输出尺寸正确、帧率稳定、两路 raw
  都是 640x400，所以它是更合适的运行配置。
