# CyberDog2 运控修改指南

官方源码入口：

- 仓库：<https://github.com/MiRoboticsLab/cyberdog_locomotion>
- 重点文件示例：<https://github.com/MiRoboticsLab/cyberdog_locomotion/blob/master/control/src/convex_mpc/convex_mpc_loco_gaits.cpp>

## 0. 先明确边界

- 本文面向 CyberDog2，不是 CyberDog 一代 DOWNLOAD USB 线刷系统镜像。
- Windows 本机不能直接运行运控产物；Windows/WSL 只负责改代码、编译、校验和上传。
- 真正能上狗运行的包必须是 Linux AArch64 ELF，不是 macOS 的 Mach-O，也不是 Windows 的 PE 格式。
- 狗的外部 IP 不固定，必须现场探测；97 号狗曾经是 `172.20.10.5`，但不能写死。
- 外层 NX 登录用户通常是 `mi`，现场默认密码是 `123`；内侧运控板通常是 `root@192.168.44.233`。
- 每次热更新前必须备份 `/robot/robot-software`，更新失败必须能回滚。

## 1. Windows/WSL 路径约定

后续命令推荐在 WSL Ubuntu 里执行。Windows 路径和 WSL 路径要区分：

```bash
sudo apt update
sudo apt install -y git openssh-client netcat-openbsd file coreutils
```

```bash
# Windows 桌面 C:\Users\你的用户名\Desktop
# 在 WSL 中写成 /mnt/c/Users/你的用户名/Desktop

WIN_USER=$(cmd.exe /c echo %USERNAME% 2>/dev/null | tr -d '\r')
WORKDIR="/mnt/c/Users/$WIN_USER/Desktop"
```

如果源码放在 WSL 自己的 Linux 文件系统里，路径可以直接用：

```bash
WORKDIR="$HOME"
```

建议把源码放在 WSL Linux 文件系统内，编译和文件权限更稳定；如果放在 `/mnt/c/...`，尽量用 `tar.gz` 分发成品包，避免 Windows 解压破坏执行权限。

## 3. 修改运控代码

本次进度里真正动到的运控核心是 `control/src/convex_mpc/convex_mpc_loco_gaits.cpp`，主要修改方向如下：

1. 处理机身高度命令：原逻辑存在硬编码高度下限，例如 `0.23`，并且 Locomotion 未完整消费外部传入的 `pos_des[2]`。
2. 把高度范围做成配置项：CyberDog2 使用更低的安全高度范围，例如进度中验证过的 `[0.16, 0.28] m`。
3. 恢复或启用地形补偿：避免坡面上仍按平地姿态和落脚高度计算。
4. 接近腿部伸展极限时降低目标高度：不能通过放宽腿长保护来解决越界。
5. 不删除腿部工作空间、电机、急停等保护链路；最多只做有明确目的、可回滚的最小改动。

相关文件可以按这个顺序检查：

```bash
control/src/convex_mpc/convex_mpc_loco_gaits.cpp
control/src/fsm_states/fsm_state_locomotion.cpp
control/include/control/user_parameters.hpp
common/config/cyberdog2-ctrl-user-parameters.yaml
common/config/cyberdog-ctrl-user-parameters.yaml
control/include/control/convex_mpc/locomotion_safety_utils.hpp
tests/locomotion_safety_utils_test.cpp
```

修改后先本地看差异：

```bash
git diff -- control/src/convex_mpc/convex_mpc_loco_gaits.cpp
git diff --check
```

如果遇到 `yaml-cpp` 版本兼容问题，不要依赖某个版本才有的 `NodeType` 类型写法；进度里的经验是改成兼容旧版交叉编译镜像的写法后，CyberDog2 交叉编译可以从缓存续编到 100%。

## 4. 交叉编译 CyberDog2

官方 README 要求实机部署产物必须在指定 Docker 镜像里交叉编译。Mac 和 Windows/WSL 的宿主路径不同，但容器内路径统一挂到 `/work/build_farm/workspace/cyberdog`。

Mac 示例：

```bash
SRC=/Users/huangzhicheng/cyberdog_locomotion
docker run -it --rm --name cyberdog2-loco-build \
  -v "$SRC:/work/build_farm/workspace/cyberdog" \
  cr.d.xiaomi.net/athena/athena_cheetah_arm64:2.0 /bin/bash
```

Windows/WSL 示例：

```bash
SRC="$HOME/cyberdog_locomotion"
docker run -it --rm --name cyberdog2-loco-build \
  -v "$SRC:/work/build_farm/workspace/cyberdog" \
  cr.d.xiaomi.net/athena/athena_cheetah_arm64:2.0 /bin/bash
```

进入容器后执行：

```bash
cd /work/build_farm/workspace/cyberdog
mkdir -p onboard-build-cyberdog2
cd onboard-build-cyberdog2

cmake \
  -DCMAKE_TOOLCHAIN_FILE=/usr/xcc/aarch64-openwrt-linux-gnu/Toolchain.cmake \
  -DONBOARD_BUILD=ON \
  -DBUILD_FACTORY=ON \
  -DBUILD_CYBERDOG2=ON \
  ..

make -j4
```

关键判断标准：

- 必须是 `BUILD_CYBERDOG2=ON`，不要误编成一代狗。
- 必须是 `ONBOARD_BUILD=ON`，否则可能只是本机验证产物。
- 构建目标系统应是 Linux/aarch64。

## 6. 校验成品包能不能给 Windows/WSL 使用

结论：不能在 Windows 本机执行，但可以在 Windows/WSL 作为上传包使用。

在 WSL 或 Mac 上检查：

```bash
PACKAGE_DIR="$SRC/onboard-build-cyberdog2/robot-software"

test -f "$PACKAGE_DIR/manager"
test -f "$PACKAGE_DIR/build/cyberdog_control"
test -f "$PACKAGE_DIR/build/libcontrol.so"

file "$PACKAGE_DIR/manager"
file "$PACKAGE_DIR/build/cyberdog_control"
file "$PACKAGE_DIR/build/libcontrol.so"

find "$PACKAGE_DIR" -type f | wc -l
du -sh "$PACKAGE_DIR"
```

判断标准：

- `manager`、`cyberdog_control`、`libcontrol.so` 应显示 `ELF 64-bit` 和 `ARM aarch64`。
- 如果显示 `Mach-O`，说明是 macOS 本机产物，不能上狗。
- 如果显示 `PE32` 或 `PE32+`，说明是 Windows 产物，不能上狗。
- 进度中验证过的 CyberDog2 部署目录约 141 个文件、约 20 MB，可作为数量级参考。

建议打包给别人时用：

```bash
tar -czf cyberdog2-robot-software-$(date +%Y%m%d-%H%M%S).tar.gz \
  -C "$(dirname "$PACKAGE_DIR")" robot-software
```

## 7. 探测狗的外部 IP

让电脑先连上机器狗热点或同一局域网，然后在 WSL 中看邻居表：

```bash
ip -4 addr
ip -4 route
ip neigh
```

可以试常见候选：

```bash
for ip in 172.20.10.1 172.20.10.2 172.20.10.5 192.168.44.1; do
  echo "try $ip"
  nc -vz -w 2 "$ip" 22
done
```

能连通 22 端口后再 SSH：

```bash
DOG_IP=替换成探测到的IP
ssh mi@"$DOG_IP"
```

如果出现 `REMOTE HOST IDENTIFICATION HAS CHANGED`，说明本机 `known_hosts` 里记录的是旧狗或旧系统指纹，确认现场网络无误后清理旧记录：

```bash
ssh-keygen -R "$DOG_IP"
ssh mi@"$DOG_IP"
```

进入 NX 后，检查能否到内侧运控板：

```bash
ping -c 1 192.168.44.233
ssh root@192.168.44.233 'uname -m; ls -ld /robot/robot-software'
```

## 8. 热更新到运控板

推荐路径是：电脑/WSL -> 狗端 NX -> 内侧运控板 `192.168.44.233`。不要直接删除线上目录，先上传到暂存目录，再备份，再切换。

先设置变量：

```bash
DOG_IP=替换成探测到的IP
BOARD_IP=192.168.44.233
PACKAGE_DIR="$SRC/onboard-build-cyberdog2/robot-software"

NX="mi@$DOG_IP"
BOARD="root@$BOARD_IP"
STAMP=$(date +%Y%m%d-%H%M%S)
```

下面命令默认交互输入密码；如果要自动化，可以在 WSL 里安装 `sshpass` 后自行包一层。

检查跳板链路：

```bash
ssh "$NX" 'hostname; whoami; ip addr show wlan0 || ip addr'
ssh -J "$NX" "$BOARD" 'uname -m; pidof manager || true; pidof cyberdog_control || true'
```

上传新包到运控板暂存目录：

```bash
scp -r -o ProxyJump="$NX" "$PACKAGE_DIR" "$BOARD:/robot/robot-software.new-$STAMP"
```

如果 `scp` 报 SFTP 兼容问题，用传统 scp 协议：

```bash
scp -O -r -o ProxyJump="$NX" "$PACKAGE_DIR" "$BOARD:/robot/robot-software.new-$STAMP"
```

切换前创建独立备份：

```bash
ssh -J "$NX" "$BOARD" "
set -eu
test -d /robot/robot-software
test ! -e /robot/robot-software.backup-$STAMP
cp -a /robot/robot-software /robot/robot-software.backup-$STAMP
test -f /robot/robot-software.backup-$STAMP/manager
test -f /robot/robot-software.backup-$STAMP/build/cyberdog_control
sync
"
```

如果源码里已有本次进度新增的安全切换脚本，上传并执行：

```bash
scp -o ProxyJump="$NX" scripts/activate_staged_locomotion.sh "$BOARD:/tmp/activate_staged_locomotion.sh"

ssh -J "$NX" "$BOARD" "
chmod +x /tmp/activate_staged_locomotion.sh
/tmp/activate_staged_locomotion.sh $STAMP
"
```

成功时应看到：

```text
ACTIVATION_OK
```

脚本会做这些事：

- 停止 `manager` 和 `cyberdog_control`。
- 将旧 `/robot/robot-software` 移到 `/robot/robot-software.previous-$STAMP`。
- 将 `/robot/robot-software.new-$STAMP` 切成新的 `/robot/robot-software`。
- 从 `/robot/robot-software/build` 启动 `manager`。
- 15 秒内等待 `manager` 和 `cyberdog_control` 同时就绪。
- 新版本启动失败时，把新目录改成 `/robot/robot-software.failed-$STAMP`，自动恢复 previous 版本。

如果当前仓库没有 `activate_staged_locomotion.sh`，先不要手动硬覆盖，参考同目录的 `CyberDog2_刷运控流程.md` 生成临时激活脚本。

## 9. 热更新后验证

```bash
ssh -J "$NX" "$BOARD" '
pidof manager
pidof cyberdog_control
readlink -f /proc/$(pidof manager | awk "{print \$1}")/exe
readlink -f /proc/$(pidof cyberdog_control | awk "{print \$1}")/exe
tail -n 120 /robot/manager.log
'
```

重点看：

- `manager` 路径应是 `/robot/robot-software/manager`。
- `cyberdog_control` 路径应是 `/robot/robot-software/build/cyberdog_control`。
- 日志里应能看到离线轨迹、FSM、LCM 周期任务正常初始化。
- 不应出现缺少步态文件、RL 模型、`cyberdog2-spi.yaml` 等资源错误。

再对核心文件做摘要检查：

```bash
ssh -J "$NX" "$BOARD" '
sha256sum \
  /robot/robot-software/manager \
  /robot/robot-software/build/cyberdog_control \
  /robot/robot-software/build/libcontrol.so
'
```

最后再做动作测试。动作测试顺序必须从低风险开始：

1. 固定机身，确认急停可用。
2. 只测试站立和低速短距离。
3. 确认没有充电/外供电导致的 `ESTOP`。
4. 再逐步测试高度、斜坡、转体或更复杂动作。

## 10. 回滚原则

优先依赖 `activate_staged_locomotion.sh` 自动回滚。如果必须手动回滚，先确认 `previous` 目录存在：

```bash
ROLLBACK_STAMP=替换成当次热更新时间戳

ssh -J "$NX" "$BOARD" "
set -eu
test -d /robot/robot-software.previous-$ROLLBACK_STAMP
for p in manager cyberdog_control; do
  ids=\$(pidof \$p 2>/dev/null || true)
  [ -n \"\$ids\" ] && kill \$ids 2>/dev/null || true
done
sleep 2
mv /robot/robot-software /robot/robot-software.failed-manual-\$(date +%Y%m%d-%H%M%S)
mv /robot/robot-software.previous-$ROLLBACK_STAMP /robot/robot-software
sync
cd /robot/robot-software/build
nohup env LD_LIBRARY_PATH=/robot/robot-software/build /robot/robot-software/manager /robot/ </dev/null >/robot/manager.log 2>&1 &
"
```

回滚后同样执行第 9 节的进程、路径和日志验证。

## 11. 常见坑

- 不要把 `build-macos/control/user/cyberdog_control` 传上狗；它只是 macOS 编译完整性验证产物。
- 不要直接沿用别人记录的狗 IP；同一只狗换热点或网络后 IP 也可能变化。
- `root@192.168.44.233` 是内侧运控板地址，通常要通过 `mi@DOG_IP` 做跳板。
- 官方 `scp_by_nx_ip.sh` 和 `nx2loco.sh` 有直接删除线上目录的逻辑，比赛现场更推荐本文的备份、暂存、切换、自动回滚流程。
- 热更新成功只代表进程启动成功，不代表动作安全；运动验证必须从固定机身、低速、小位移开始。
- 不要为了让动作跑起来删除 `CheckLegWorkspace`、电机保护、急停或底层保护。
